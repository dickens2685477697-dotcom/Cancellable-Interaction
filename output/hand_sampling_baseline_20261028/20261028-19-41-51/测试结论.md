## 三种现象应分别理解

1. **FixedUpdate 消费读取重复：39 次，占 2.73%。** 全部与紧邻前一条记录具有相同应用帧、样本序号和样本接收时间；逻辑 fixedTime 增加约 20 ms，但两次 FixedUpdate 消费读取的记录实际相隔中位数 0.422 ms，范围 0.365–3.644 ms。39 条全部为 `sampleAccepted=False`、`selected=False`。例如 common-motion 第 115、116 行，同为帧 98117、样本 959；实际相隔 0.463 ms。
2. **两个 Provider 来源重复发布同一状态。** 窗口内 4,056 条 MRTK 手部事件对应 2,028 个骨架引用的 SDK 读取状态；每个状态都由两个不同 SourceId 在同一应用帧发布。生效 Input Profile 第 91、105 行注册了相同的 `OculusXRSDKDeviceManager`。不能把合计约 142 次/秒称作硬件采样率。当前共享消费固定一个 SourceId，因此这类双来源发布没有直接变成双倍运动处理。
3. **FixedUpdate 消费读取最新值时略过中间事件。** 所选来源在统计窗口发布 2,028 次，其中 1,389 次被本目标接受，639 次没有被本目标接受。总接受数 1,390 中，有一份基准样本在窗口开始前已发布。MRTK 以约 71 Hz 发布、FixedUpdate 以约 50 Hz 消费读取最新值，会略过中间事件；此数不代表传感器或传输丢包。

## 软件链路中的时间差

全部 1,429 条 FixedUpdate 消费读取都精确关联到所选 MRTK 样本序号；通过同侧唯一骨架和三个关节位置一致的匹配，又关联到候选 SDK 读取状态。以下时间差都使用 Unity realtime，同一时钟相减。

| 阶段 | 中位数 | P99 | 最大 |
|---|---:|---:|---:|
| 候选 SDK 调用返回 → MRTK 事件接收 | 13.44 ms | 24.19 ms | 28.47 ms |
| MRTK 事件接收 → FixedUpdate 消费读取 | 13.76 ms | 27.50 ms | 28.56 ms |
| 候选 SDK 调用返回 → FixedUpdate 消费读取 | **27.36 ms** | **41.20 ms** | **41.83 ms** |

本次候选关联记录全部呈现：SDK 读取位于 Unity 应用帧 N，MRTK 事件接收位于应用帧 N+1，FixedUpdate 消费读取位于应用帧 N+2。这里的帧均指 Unity 应用帧。源码也与此一致：MRTK 的执行序号为 -100，OVRHand 为 -90，OVRSkeleton 为 -80；当前 FixedUpdate 消费读取发生在该应用帧 Update 之前。

这是软件观察点之间的时间差。骨架位置匹配属于候选关联，不能替代 SDK 直接贯穿各层的硬件帧编号；也不能将 27.36 ms 称为相机曝光至选择或显示的端到端延迟。

## 硬件第一时间能否保证

**当前不能保证。** 2,028 次有效 SDK 读取中的 2,027 对连续 `SampleTimeStamp` 没有完全相等的值，但所有记录的 `SampleTimeStamp` 都等于 `RequestedTimeStamp`；其中最短时间差甚至约 1 纳秒。因此时间戳变化本身不能证明相机生成了新帧。现有 `GetHandState` 返回预测姿态，日志记录的是它返回后的软件观察点，没有相机曝光时间或原始硬件帧 ID。

当前结论适用于此次 Editor + Link、约 71 FPS、50 Hz、开启诊断的配置；频率改变后重复率可能不同。诊断本身也可能带来开销。本次尚未修改更新方式或 Provider 配置。

后续宜先单独消除 Provider 重复注册并复测，再分别比较保持 FixedUpdate 与在 MRTK 数据发布后消费新样本的方案。单纯改用任意 Update，并不能同时解决更新顺序、双来源发布和硬件帧身份问题。
